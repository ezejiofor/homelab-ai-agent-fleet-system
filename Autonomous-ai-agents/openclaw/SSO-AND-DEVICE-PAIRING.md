# OpenClaw — SSO + Device Pairing Runbook

End-to-end browser access to the OpenClaw Control UI at
`https://openclaw.georgehomelab.com` goes through **three** independent
auth layers. All three must succeed before the WebSocket holds open.

```
Browser ─┬─► Istio Gateway ─► oauth2-proxy ─► OpenClaw gateway (port 18789)
         │                                    │
         │   1. Keycloak OIDC (Google/GitHub)  │   2. Gateway token (shared secret)
         │      handled by oauth2-proxy        │   3. Device pairing (per-browser)
         │                                    │
         └────────── browser pastes WS URL + token in Control UI form
```

| Layer | Enforced by | What can go wrong | Where to look |
|---|---|---|---|
| **OIDC** | oauth2-proxy + Keycloak realm `openclaw` | `invalid_scope`, `unauthorized_client`, "Authenticated" blank page | oauth2-proxy pod logs in `agents-system` |
| **Gateway token** | OpenClaw `gateway.auth.mode: token` | `auth failed` in WS handshake | `OPENCLAW_GATEWAY_TOKEN` env on the pod |
| **Device pairing** | OpenClaw `device-pair` plugin | `pairing required: device is not approved yet` | `openclaw devices list` inside the pod |

---

## Defense-in-depth: how the three layers stack

The layers are **independent** — each one denies the WebSocket on its own,
so an attacker has to defeat *all three* to reach the Control UI.

```
Browser
  │
  │  Layer 1: Keycloak OIDC (via oauth2-proxy)
  │  ──────────────────────────────────────────
  │  • oauth2-proxy intercepts every request to
  │    https://openclaw.georgehomelab.com.
  │  • Redirects unauthenticated users to Keycloak login (Google or GitHub).
  │  • Sets a session cookie on success.
  │  • Stops anonymous internet traffic at the edge — without a valid
  │    Keycloak session, you never reach the OpenClaw gateway at all.
  ▼
oauth2-proxy (reverse-proxies to the OpenClaw Service in agents-system)
  │
  │  Layer 2: Gateway shared-secret token
  │  ─────────────────────────────────────
  │  • OpenClaw's `gateway.auth.mode: token` requires every WebSocket
  │    handshake to present OPENCLAW_GATEWAY_TOKEN in
  │    connect.params.auth.token.
  │  • Token is a 32-byte hex value, stored in Vault, synced via VSO,
  │    rotatable independently of any user's credentials.
  │  • Stops a Keycloak-authenticated user from connecting via a different
  │    path (kubectl port-forward, internal Service, sibling pod) — they'd
  │    still need the shared secret.
  ▼
OpenClaw gateway accepts the WS connect frame
  │
  │  Layer 3: Per-browser device pairing
  │  ────────────────────────────────────
  │  • OpenClaw's device-pair plugin records every new browser fingerprint
  │    as a "pending pairing request".
  │  • The WebSocket is rejected with `pairing required: device is not
  │    approved yet` until an operator runs `openclaw devices approve
  │    <requestId>` inside the pod.
  │  • Even if Layers 1 and 2 are both compromised, an attacker on a new
  │    browser/device cannot connect without admin-side approval.
  │  • Approved devices persist in the PVC; pairing is one-time per
  │    browser fingerprint.
  ▼
WebSocket holds open → Control UI loads
```

### What each layer is genuinely buying you

- **L1 alone** would let any Keycloak user with cluster access reach the
  OpenClaw API directly — e.g. via `kubectl port-forward` to the openclaw
  Service, bypassing oauth2-proxy entirely.
- **L1 + L2** stops that. You'd need the shared token too. But if the token
  leaks (committed to git, pasted into Slack, exposed in a stale terraform
  plan), an attacker with a Keycloak session can connect from any browser.
- **L1 + L2 + L3** stops that. Even with Keycloak + shared token, an
  attacker on a never-seen-before device gets parked in the pending queue
  until you approve them via `openclaw devices approve`.

L3 is the only layer that's bound to a *device fingerprint* rather than a
*credential*, which is why it's the strongest individual layer.

### Operational trade-off

Every fresh browser, incognito session, or wiped browser storage produces a
new pending request that must be approved through the gateway CLI. The PVC
keeps approvals durable, so it's truly one-time per browser fingerprint
unless site data is cleared or the PVC is wiped.

## Layer 1 — Keycloak OIDC (oauth2-proxy)

- Realm: `openclaw` (generated by `keycloak/realms/gen_realms.py`).
- Client: `oauth2-proxy` (confidential, secret stored in K8s Secret
  `oauth2-proxy-openclaw` in the `agents-system` namespace).
- oauth2-proxy overlay: `kubernetes-addons/0-boostrap/oauth2-proxy/overlays/openclaw/`.

If the K8s secret drifts from Keycloak (after re-importing a realm), token
exchange fails with `unauthorized_client / Invalid client or Invalid client
credentials`. Re-sync:

```bash
cd kubernetes-addons/0-boostrap/oauth2-proxy/overlays
yes y | python3 openclaw/setup-secret.py
kubectl -n agents-system rollout restart deploy/oauth2-proxy-openclaw
```

If oauth2-proxy returns a literal `Authenticated` 200 instead of the OpenClaw
UI, the base config's `--upstream=static://200` (ExtAuthz mode) is overriding
the env var. The fix is in this overlay's `kustomization.yaml` — a JSON6902
patch that replaces that arg with the real upstream URL.

## Layer 2 — Gateway shared-secret token

OpenClaw's `gateway.auth.mode: token` requires the Control UI form to receive
the same token the gateway process loaded from `OPENCLAW_GATEWAY_TOKEN`.

The token lives in Vault at `secret/homelab/ai-agents/openclaw`, synced into
K8s Secret `openclaw-secrets` by VSO, and is sourced from
`terraform/vault-config/environment/prod/.secrets.auto.tfvars` (Terraform is
the source of truth — `lifecycle.ignore_changes` is intentionally OFF).

### Generate a fresh token

```bash
NEW_TOKEN=$(openssl rand -hex 32)
echo "$NEW_TOKEN"

# 1. Edit terraform/vault-config/environment/prod/.secrets.auto.tfvars
#    OPENCLAW_GATEWAY_TOKEN = "<NEW_TOKEN>"

# 2. Refresh the JWT (Keycloak short-lived) and apply
cd terraform/vault-config/environment/prod
bash scripts/refresh-jwt.sh
terraform apply -target='module.secrets.vault_kv_secret_v2.ai_openclaw' -auto-approve

# 3. Force VSO to re-sync immediately (otherwise it waits up to refreshAfter=1h)
kubectl -n agents-system annotate vaultstaticsecret openclaw-secrets \
  vault.hashicorp.com/refresh-now="$(date +%s)" --overwrite

# 4. The deployment auto-restarts via VSO's rolloutRestartTargets.
#    Verify the new token landed:
kubectl -n agents-system get secret openclaw-secrets \
  -o jsonpath='{.data.OPENCLAW_GATEWAY_TOKEN}' | base64 -d ; echo
```

Paste the new token into the Control UI's **Gateway Token** field.

### Read the current token

```bash
kubectl -n agents-system get secret openclaw-secrets \
  -o jsonpath='{.data.OPENCLAW_GATEWAY_TOKEN}' | base64 -d ; echo
```

## Layer 3 — Device pairing (the part everyone forgets)

The first time a new browser connects, the gateway records a **pending pairing
request** and refuses the WebSocket with:

```
pairing required: device is not approved yet (requestId: <UUID>)
```

This is enforced by the `device-pair` plugin and is *not* something the
gateway token alone satisfies. Each unique browser fingerprint gets one
pending request per attempt.

### Approve a pending request

```bash
POD=$(kubectl -n agents-system get pod -l app.kubernetes.io/name=openclaw \
  --field-selector=status.phase=Running -o jsonpath='{.items[0].metadata.name}')

# 1. List pending + paired devices
kubectl -n agents-system exec $POD -c gateway -- openclaw devices list

# 2. Approve by requestId (UUID from the "Pending" table or pod logs)
kubectl -n agents-system exec $POD -c gateway -- \
  openclaw devices approve <requestId>
```

The user can now click **Connect** in the Control UI and the WebSocket holds
open. Approved devices persist in the PVC at `/home/node/.openclaw/identity/`,
so re-pairing is only needed if the browser fingerprint changes (different
browser, cleared site data, incognito) or the PVC is wiped.

### Other useful subcommands

```bash
# List paired devices
openclaw devices list

# Reject a pending request instead of approving
openclaw devices reject <requestId>

# Remove a previously paired device (forces re-pairing on next connect)
openclaw devices remove <deviceId>

# Rotate a device's token in place
openclaw devices rotate <deviceId>

# Revoke all tokens for a device
openclaw devices revoke <deviceId>
```

### What the request entry looks like

```
Pending (1)
┌──────────────────────────────────────┬───────────────┬──────────────────────┐
│ Request                              │ Device        │ Requested            │
├──────────────────────────────────────┼───────────────┼──────────────────────┤
│ e68a26c0-76fc-41b6-8e48-926c85c07a75 │ b9b591c46b…   │ roles: operator;     │
│                                      │               │ scopes: operator.    │
│                                      │               │ admin, operator.     │
│                                      │               │ approvals, …         │
└──────────────────────────────────────┴───────────────┴──────────────────────┘
```

The 32-character hex string in **Device** is the device fingerprint (derived
from the browser's WebCrypto keypair). The UUID in **Request** is what
`devices approve` consumes.

## ConfigMap requirements (origin allowlist)

Because the Control UI is reached via Istio ingress (not loopback), the
gateway requires the origin to be explicitly allowlisted. The configmap in
this folder enforces:

```jsonc
"gateway": {
  "mode": "local",
  "bind": "lan",
  "controlUi": {
    "enabled": true,
    "allowedOrigins": ["https://openclaw.georgehomelab.com"]
  }
}
```

`mode` must remain `local` — `remote` is not a valid value and the gateway
will refuse to start. The init container `init-config` copies this configmap
to the PVC at `/home/node/.openclaw/openclaw.json` on every pod restart, but
**ArgoCD owns this configmap on the cluster** — local `kubectl apply` edits
will be reverted on the next sync. To change anything here, edit the file,
commit, push, and let ArgoCD sync (or trigger a sync manually):

```bash
kubectl -n argocd patch application agent-openclaw \
  --type merge --patch '{"operation":{"sync":{}}}'
```

## End-to-end recovery checklist

When `https://openclaw.georgehomelab.com/chat?session=main` does *not* load:

1. **Blank "Authenticated" page** → oauth2-proxy upstream args drift; check
   the JSON6902 patch in
   `kubernetes-addons/0-boostrap/oauth2-proxy/overlays/openclaw/kustomization.yaml`
   still resolves `--upstream=static://200` correctly.
2. **`invalid_scope` after Keycloak login** → realm regenerated without the
   11 standard scopes; re-run `keycloak/realms/gen_realms.py` and re-import.
3. **`unauthorized_client / Invalid client credentials`** → run
   `setup-secret.py` to re-sync the K8s Secret with the live Keycloak client
   secret.
4. **`origin not allowed` in pod logs** → `allowedOrigins` missing from
   configmap, or pod is reading a stale copy from PVC. Confirm with
   `kubectl exec ... cat /home/node/.openclaw/openclaw.json`. If the PVC
   copy is stale and the configmap is correct, restart the pod (the init
   container will overwrite the PVC copy from the configmap).
5. **`pairing required: device is not approved yet`** → run
   `openclaw devices approve <requestId>` inside the pod.
